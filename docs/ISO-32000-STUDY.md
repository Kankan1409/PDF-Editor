# ISO 32000 กับการพัฒนา Smart PDF Editor

วันที่ศึกษา: 15 ตุลาคม 2026

## ขอบเขตและข้อสรุป

รายงานนี้เป็นการศึกษาทางวิศวกรรมเพื่อแก้ปัญหาฟอนต์ไทย การแก้ข้อความเดิม และการแทนที่ชื่อบุคคลใน Smart PDF Editor ไม่ใช่ใบรับรองความสอดคล้องกับ ISO และไม่ใช่คำอธิบายระบบภายในของ Adobe Acrobat ซึ่งไม่ได้ตรวจสอบในงานนี้

อ่านส่วนที่เกี่ยวข้องของ PDF 32000-1:2008 ฉบับเผยแพร่โดย Adobe ประกอบกับข้อมูลสถานะของ ISO และข้อแก้ไข ISO 32000-2:2020 จาก PDF Association พร้อมตรวจโค้ดปัจจุบันของโครงการ ยังไม่ได้อ่าน ISO 32000-2:2020 ฉบับเต็มทุกบท: ช่องทาง sponsored access มีขั้นตอนรับเอกสารที่ยังไม่ได้ดำเนินการ ข้อแก้ไขออนไลน์เป็นส่วนเพิ่มเติม ไม่สามารถแทนมาตรฐานฉบับเต็มได้

**ข้อสรุปสำหรับโครงการ:** ต้องพัฒนาการจับคู่ข้อความกับคำสั่งใน PDF การจัดรูปอักษร และการตรวจผลหลังแก้ควบคู่กับคลังฟอนต์ การติดตั้งฟอนต์เพิ่มเพียงอย่างเดียวไม่ทำให้แก้ PDF ทุกไฟล์ได้เหมือนต้นฉบับ

ในรายงานนี้ “ข้อกำหนด/กลไกมาตรฐาน” หมายถึงสิ่งที่อ้างอิงจากเอกสาร ส่วน “ข้อเสนอ” คือแนวทางออกแบบของเรา ไม่ใช่ข้อบังคับของ ISO

## 1. มาตรฐานแต่ละฉบับใช้กับอะไร

| เอกสาร | ความเกี่ยวข้อง |
|---|---|
| ISO 32000-1:2008 | PDF 1.7 ซึ่งยังสำคัญกับไฟล์ที่ผู้ใช้มีอยู่ |
| ISO 32000-2:2017 | PDF 2.0 ฉบับแรก ถูกแทนที่ด้วยฉบับ 2020 |
| ISO 32000-2:2020 | PDF 2.0 ฉบับที่สอง เป็นฉบับที่ ISO แสดงว่าทบทวนและยืนยันในปี 2026 |
| Errata และเอกสารส่วนขยาย | ต้องอ่านพร้อมฉบับฐาน และแยกสถานะข้อแก้ไขที่อนุมัติแล้วออกจากประเด็นที่ยังอภิปราย |

แหล่งอ้างอิง: [ISO 32000-2:2020](https://www.iso.org/standard/75839.html), [PDF standards](https://pdfa.org/pdf-standards/), [Errata](https://pdf-issues.pdfa.org/32000-2-2020/).

ISO 32000 อธิบายรูปแบบข้อมูลและการประมวลผล PDF ไม่ได้ระบุหน้าตาปุ่มแก้ไข วิธีเลือกย่อหน้า Undo/Redo หรือประสบการณ์ค้นหาแล้วแทนที่แบบ Acrobat การทำให้ใช้สะดวกเป็นงานอีกชั้นของแอปพลิเคชัน

PDF/A, PDF/UA และ PDF/X มีเป้าหมายและข้อกำหนดเพิ่มเติมต่างกัน การเขียนไฟล์ PDF เปิดได้ไม่ได้หมายความว่าผ่านทุกมาตรฐาน และการผ่าน PDF/A ไม่ได้พิสูจน์ว่าข้อความที่ผู้ใช้แก้ถูกต้องตามเจตนา ดู [ภาพรวมมาตรฐาน PDF](https://pdfa.org/pdf-standards/).

## 2. โครงสร้างที่ตัวแก้ไขต้องเข้าใจ

หัวข้อหลักสำหรับศึกษา: บท 7 Syntax, บท 8 Graphics, บท 9 Text, บท 10 Rendering, บท 11 Transparency, บท 12 Interactive features และบท 14 Document interchange

PDF ประกอบด้วย objects, streams, ตารางหรือสตรีม cross-reference, catalog และ page tree หนึ่งหน้ามี content streams และ resources ที่อาจอ้างอิงหรือใช้ร่วมกัน เอกสารอาจถูกบีบอัด เข้ารหัส หรือมีหลาย revision จึงไม่ควรค้นหาชื่อแล้วแทน bytes ตรง ๆ ทั้งไฟล์ แหล่งอ่าน: [Syntax และข้อแก้ไข](https://pdf-issues.pdfa.org/32000-2-2020/clause07.html).

ข้อเสนอสำหรับเรา:

- ใช้ parser ที่เข้าใจโครงสร้าง PDF ไม่ใช้ regex เป็นตัวแก้ content stream หลัก
- เก็บตำแหน่งต้นทางของข้อความ: object, stream, operator, operand และเส้นทางการเรียก Form XObject
- ถ้า Form XObject เดียวถูกแสดงหลายตำแหน่ง การแก้เพียงหนึ่งตำแหน่งต้องทำสำเนา instance ที่เกี่ยวข้องและแก้การอ้างอิง ไม่แก้ resource ร่วมโดยไม่ตั้งใจ
- เคารพขอบเขต resource dictionary และ graphics state ของแต่ละตำแหน่ง
- ระบุขอบเขตที่รองรับก่อนลงมือ เช่น ข้อความแนวนอนธรรมดา ก่อนขยายสู่ข้อความตัดกับ clipping หรือ transparency group

ตัวอย่างความเสี่ยง: ชื่อเดียวกันอยู่ในหัวกระดาษที่ใช้ Form XObject ร่วมกันสามหน้า ผู้ใช้เลือก “แก้จุดนี้” ต้องเปลี่ยนเพียงจุดที่เลือก ไม่ใช่ทุก instance ของ object นั้น

## 3. ข้อความที่เห็น รหัสในไฟล์ และ Unicode เป็นคนละชั้น

สำหรับกรณี Type 0 font ที่มี CIDFontType2 เส้นทางหลักคือ:

```text
bytes ของคำสั่งแสดงข้อความ
    → Encoding CMap → CID → CIDToGIDMap → glyph ในฟอนต์ → ภาพบนหน้า

bytes ของคำสั่งแสดงข้อความ
    → ToUnicode → ลำดับ Unicode สำหรับการนำข้อความไปใช้
```

แผนภาพนี้ไม่ครอบคลุม font ทุกชนิด: simple fonts, CFF และ Type 3 ต้องตีความตามชนิดนั้น การใช้ `/Identity-H` ไม่ได้พิสูจน์ว่า CID เท่ากับ glyph ID เพราะยังต้องตรวจการจับคู่ของ descendant font ด้วย ดู PDF 32000-1 ข้อ 9.7 และ 9.10 จาก [ฉบับ Adobe](https://opensource.adobe.com/dc-acrobat-sdk-docs/pdfstandards/PDF32000_2008.pdf).

`ToUnicode` จับคู่ **character code ของ PDF** กับ Unicode ไม่ใช่จับคู่ชื่อฟอนต์กับตัวอักษร การเพิ่ม ToUnicode อาจแก้การคัดลอกหรือค้นหา แต่ไม่ได้สร้าง glyph ที่ฟอนต์ขาด และไม่เปลี่ยนภาพที่วาดโดยอัตโนมัติ ดู [ข้อแก้ไขบท Text ข้อ 9.7.6 และ 9.10](https://pdf-issues.pdfa.org/32000-2-2020/clause09.html).

ตัวอย่างสมมติของเรา: code `002A` อาจเลือก CID 42 แล้วถูกแปลงเป็น glyph 17 ซึ่งวาด “ก” การเขียน ToUnicode ที่ key `0011` เพราะคิดว่า code เป็น glyph 17 จึงผิด แม้ภาพยังดูเป็น “ก” ได้

ข้อเสนอ: เก็บ mapping ทั้งสองเส้นทางอย่างชัดเจน หากระบุความหมายไม่ได้ให้แสดงสถานะไม่แน่นอน ห้ามใช้ภาพเหมือนกันเป็นหลักฐานเพียงอย่างเดียวว่ามี Unicode เดียวกัน

## 4. ฟอนต์เดิม: ชื่อเหมือนกันยังไม่พอ

ฟอนต์ฝังใน PDF อาจมีเพียง subset ของตัวอักษร การแก้จากชื่อเก่าเป็นชื่อใหม่จึงอาจต้องใช้ glyph ที่ไม่อยู่ในไฟล์ Font descriptor และ metrics อ้างอิง font program ที่ใช้จริง ไม่ใช่แค่ข้อความชื่อฟอนต์ ดู [Text: CID subsets และ Font descriptors](https://pdf-issues.pdfa.org/32000-2-2020/clause09.html).

ข้อเสนอสำหรับคลังฟอนต์:

1. ตรวจ font program ที่ฝังอยู่และตัวอักษรที่ต้องใช้ก่อน
2. หากไม่พอ ตรวจไฟล์เต็มของ font face เดิม รวมรุ่น น้ำหนัก ความเอียง และ metrics
3. แสดง alias เพื่อช่วยค้นหาได้ แต่ห้ามถือว่า alias รับรองว่า font bytes หรือรูปอักษรเหมือนกัน
4. ถ้าใช้ฟอนต์อื่น ให้ผู้ใช้เลือกอย่างชัดเจน พร้อมเห็นผลบน PDF จริง
5. เก็บที่มา รุ่น hash และเงื่อนไขการใช้งานของฟอนต์ที่จัดส่งกับโปรแกรม

สำหรับ THSarabunPSK / THSarabun ควรตรวจชื่อภายในไฟล์จริงและแสดงชื่อที่ผู้ใช้ค้นหาได้ การเรียกชื่อสองแบบไม่ได้ทำให้มีสอง font program และไม่ควรนำ Sarabun หรือ TH Sarabun New มาอ้างว่าเป็น PSK เดิมโดยไม่ตรวจ

สิทธิ์ฝังฟอนต์เป็นอีกมิติหนึ่ง OpenType `OS/2.fsType` แยก restricted, preview/print, editable, no-subsetting และ bitmap-only ต้องตีความตามรุ่นตารางและเงื่อนไขเจ้าของฟอนต์ ไม่ควรปิดข้อจำกัดเพื่อให้การแก้ผ่าน และ no-subsetting ไม่ได้แปลว่าห้ามฝังไฟล์เต็มทุกกรณี ดู [OpenType OS/2 fsType](https://learn.microsoft.com/en-us/typography/opentype/spec/os2#fstype).

## 5. ภาษาไทยต้องจัดรูปอักษรและเก็บความสัมพันธ์กับข้อความ

การมี Unicode ครบใน cmap ไม่ได้พิสูจน์ว่าการวางสระและวรรณยุกต์ถูกต้อง ต้องจัดรูปอักษรตาม font, script, language และบริบท เครื่องมือ shaping เช่น HarfBuzz ให้ผลเป็น glyphs และตำแหน่ง โดยอาศัยข้อมูล layout ของฟอนต์ ดู [HarfBuzz: shaping](https://harfbuzz.github.io/what-is-harfbuzz.html).

ข้อเสนอสำหรับ editor:

- เก็บ Unicode ต้นทางและความสัมพันธ์ระหว่างช่วงข้อความกับ glyph clusters ระหว่าง shaping
- การเลือกและลบต้องไม่ตัดสระหรือวรรณยุกต์ออกจากกลุ่มที่ต้องประมวลผลร่วมกัน
- กำหนดช่วง reshape ตามบริบทของ script; การแก้หนึ่งตัวอักษรอาจต้องจัดรูปใหม่ทั้งกลุ่มหรือ run
- อย่าสร้าง Unicode ย้อนกลับจาก glyph outline อย่างเดียว เพราะหลายตัวอักษรหรือหลายลำดับอาจมีรูปร่างเหมือนกัน
- หากรวม font subsets ต้องตรวจ GSUB/GPOS/AAT ที่เกี่ยวข้อง การตรวจเส้นขอบและความกว้างเท่ากันยังไม่ยืนยันว่าการจัดรูปเหมือนเดิม

กรณีทดสอบของเรา: “ต้อนรับ”, “น้ำ”, “ปิ่น”, ชื่อที่มีสระบน/ล่างและวรรณยุกต์ รวมภาษาอังกฤษ ตัวเลข และเครื่องหมายในบรรทัดเดียว

## 6. รักษาตำแหน่งหมายถึงมากกว่า x, y และขนาดฟอนต์

คำสั่งข้อความสัมพันธ์กับ text matrix, current transformation matrix และ text state เช่น character spacing, word spacing, horizontal scaling, rise และ rendering mode การคง baseline กับขนาดอย่างเดียวจึงยังไม่พอ โดย `TJ` ยังระบุระยะขยับระหว่างชิ้นข้อความได้ ดู [PDF 32000-1 ข้อ 9.3–9.4](https://opensource.adobe.com/dc-acrobat-sdk-docs/pdfstandards/PDF32000_2008.pdf) และ [ข้อแก้ไข Text](https://pdf-issues.pdfa.org/32000-2-2020/clause09.html).

ข้อเสนอด้านข้อมูลที่ต้องเก็บ:

| กลุ่ม | ข้อมูลสำหรับแผนแก้ไข |
|---|---|
| ข้อความ | Unicode, ช่วง source operators, glyph clusters, font reference |
| รูปทรง | Tm, CTM, baseline, advance, Tc, Tw, Tz, Ts, TJ |
| การวาด | Tr, fill/stroke, color space, opacity, clip และลำดับการวาด |
| หน้า | MediaBox, CropBox, Rotate, UserUnit และการแปลงพิกัดไป viewer |
| ความหมาย | marked content, ActualText, structure association ที่เกี่ยวข้อง |

ข้อมูลตารางนี้เป็นข้อเสนอของ editor ไม่ใช่ schema ที่ ISO บังคับให้แอปต้องใช้ สี CMYK/spot และภาพโปร่งใสไม่ควรถูกยุบเป็น RGB hex แล้วอ้างว่าคงต้นฉบับทุกด้าน ดูหัวข้อที่เกี่ยวข้องใน [Graphics](https://pdf-issues.pdfa.org/32000-2-2020/clause08.html) และ [Transparency](https://pdf-issues.pdfa.org/32000-2-2020/clause11.html).

การพิมพ์ใน HTML textarea ใช้เป็นเครื่องมือรับข้อความได้ แต่ภาพหลังบันทึกควรมาจาก PDF ที่สร้างจริง มิฉะนั้น browser กับ PDF renderer อาจวางอักษรและระยะไม่เหมือนกัน

## 7. การแก้เฉพาะคำ การลบข้อความ และโครงสร้างความหมาย

ข้อเสนอแบ่งวิธีแก้ตามความสามารถที่พิสูจน์ได้:

| วิธี | ใช้เมื่อ | สิ่งที่ต้องตรวจ |
|---|---|---|
| แก้ source text run | ระบุคำสั่งและ mapping ได้ครบ | State หลัง run, spacing, cluster และผลต่อข้อความข้างเคียง |
| สร้าง run ทดแทนเฉพาะส่วน | ฟอนต์/การจัดรูปใหม่จำเป็น แต่ขอบเขตปลอดภัย | ลบ glyph เดิมจริง รักษา clip และลำดับการวาด |
| แปลงบริเวณภาพสแกน | ต้นฉบับไม่มีข้อความจริง | เปลี่ยนพิกเซล/ภาพบริเวณนั้นอย่างชัดเจน พร้อมตรวจผล |
| ขอให้เลือกฟอนต์หรือวิธีอื่น | ไม่มีข้อมูลเพียงพอ | อธิบายข้อจำกัดเฉพาะจุด ไม่แสร้งทำว่าแก้สำเร็จ |

การใช้ redaction ลบข้อความแล้วเขียนใหม่ไม่ใช่วิธีที่ ISO ห้าม แต่ความถูกต้องของไฟล์และการรักษารูปเดิมเป็นคนละคำถาม ส่วนสี่เหลี่ยมทับอักษรไม่ได้รับประกันว่าข้อความเดิมหายจากไฟล์

นอกจากภาพ ยังมี `ActualText` ซึ่งเป็นข้อความแทนเนื้อหาสำหรับการนำข้อความไปใช้ หากแก้ภาพที่เห็นแต่ปล่อย ActualText เดิม อาจคัดลอกได้ชื่อเก่า ต้องตรวจ marked content และโครงสร้างที่เกี่ยวข้องด้วย ดู [PDF 32000-1 ข้อ 14.9.4](https://opensource.adobe.com/dc-acrobat-sdk-docs/pdfstandards/PDF32000_2008.pdf) และ [Document interchange errata](https://pdf-issues.pdfa.org/32000-2-2020/clause14.html).

แบบฟอร์มต้องแยกออกจากข้อความบนหน้า: ค่า field และ appearance ของ widget ต้องสอดคล้องกัน การวาดข้อความใหม่บนหน้าอย่างเดียวไม่ใช่การแก้ค่า field ดู [Interactive features](https://pdf-issues.pdfa.org/32000-2-2020/clause12.html).

ข้อเสนอสำหรับ OCR: เก็บผลรับรู้เป็นข้อมูลช่วยเลือก พร้อมความเชื่อมั่นและตำแหน่ง ภาพสแกนที่มี hidden OCR text ยังต้องแก้ภาพหากต้องการเปลี่ยนตัวอักษรที่มองเห็น การเปลี่ยนเฉพาะ hidden text ไม่บรรลุผลนี้

## 8. ค้นหาชื่อ: จุดเดียว ทั้งหมด และไล่ทีละจุด

ฟังก์ชันเหล่านี้เป็นพฤติกรรมผลิตภัณฑ์ของเรา ไม่ใช่สิ่งที่ ISO ออกแบบ UI ให้ ข้อเสนอคือใช้ดัชนีข้อความที่ย้อนกลับไปยัง source runs และ clusters ได้

1. เมื่อค้นหา แสดงจำนวนผล หน้าที่พบ และเน้นช่วงชื่อจริง
2. “แก้จุดนี้” ผูกกับ occurrence และ revision ที่ผู้ใช้เลือก
3. “แก้แล้วไปถัดไป” บันทึกสำเร็จก่อนสร้างรายการผลใหม่ มีปุ่มข้ามและย้อนกลับ
4. “แก้ทั้งหมด” วางแผนทุกตำแหน่ง ตรวจฟอนต์และพื้นที่ก่อน commit เป็นธุรกรรมเดียว
5. หากจุดหนึ่งทำไม่ได้ ให้แสดงจุดและสาเหตุ ไม่แก้บางส่วนอย่างเงียบ ๆ
6. Undo หนึ่งครั้งควรย้อนทั้งคำสั่ง “แก้ทั้งหมด” และไม่ปะปนกับ revision ของผู้ใช้อื่น

ต้องกำหนดพฤติกรรมเรื่องช่องว่าง ข้ามบรรทัด และตัวพิมพ์ให้ชัด โดยเฉพาะภาษาไทยที่ไม่ควรใช้การแยกคำแบบภาษาอังกฤษอย่างเดียว ชื่อเดียวกันอาจถูกเก็บเป็นหลาย spans หรือหลายคำสั่ง การค้นหาเฉพาะ string ของบรรทัดที่ extract ได้จึงมีขอบเขตจำกัด

ข้อเสนอด้านความถูกต้อง: เก็บข้อความต้นฉบับเต็ม แยก search normalization ออกจาก export verification และห้ามใช้การลบช่องว่างทั้งหมดเป็นตัวตัดสินว่าบันทึกถูกต้องแล้ว

## 9. การบันทึก สิทธิ์ และลายเซ็น

Incremental update เพิ่ม revision ต่อท้ายและเก็บข้อมูลเดิมไว้ จึงไม่เหมาะจะใช้เป็นหลักฐานว่าข้อมูลที่ลบถูกกำจัดแล้วทั้งหมด ลายเซ็นต้องตรวจทั้ง signed byte range และข้อจำกัดการเปลี่ยนแปลง เช่น DocMDP การคง bytes ของ revision ที่ลงนามไว้ไม่ได้ทำให้เนื้อหาที่แก้ใหม่ได้รับการรับรองโดยลายเซ็นเดิม ดู [PDF 32000-1 ข้อ 7.5.6 และ 12.8](https://opensource.adobe.com/dc-acrobat-sdk-docs/pdfstandards/PDF32000_2008.pdf).

ข้อเสนอ: แยก empty signature field, signed field, cryptographic validity และ permission ออกจากกัน โครงการปัจจุบันเลือกบล็อกเมื่อพบฟิลด์ลายเซ็น ซึ่งเป็นขอบเขต MVP แบบระมัดระวัง ไม่ใช่การตรวจความถูกต้องลายเซ็นครบถ้วน

การ full rewrite ก็ไม่รับประกันการลบชื่อเดิมจากทุกที่ ชื่ออาจอยู่ใน metadata, attachments, form values หรือโครงสร้างอื่น จึงควรแยก “แก้ข้อความบนหน้า” ออกจาก “ลบข้อมูลลับทั้งเอกสาร” ในขอบเขตผลิตภัณฑ์

## 10. สิ่งที่พบจากโค้ดของเรา

ตารางนี้เป็นผลตรวจ source code ณ วันที่ศึกษา ไม่ใช่ผลทดสอบสร้างไฟล์เสียหายครบทุกกรณี และไม่ได้ยืนยันว่าปัญหาทั้งหมดเกิดกับไฟล์ที่ผู้ใช้ส่งมา

ตำแหน่งหลัก: `backend/app/pdf_engine.py` เลขบรรทัดอาจเปลี่ยนเมื่อแก้โค้ด

| ลำดับ | หลักฐานในโค้ด | ความเสี่ยง/งานที่ต้องทำ |
|---|---|---|
| P0 | `canonical()` บรรทัด 21 ใช้ NFKC แล้วลบ whitespace ทั้งหมด | อาจยอมรับข้อความที่ช่องว่างหรือ compatibility characters เปลี่ยน ต้องตรวจข้อความเป้าหมายอย่างมีนโยบายชัดเจน |
| P0 | `apply()` บรรทัด 466 ตรวจข้อความด้วย substring ของข้อความรวมทั้งหน้า | ข้อความเหมือนกันอีกจุดอาจทำให้ผ่าน ต้องตรวจตำแหน่งและจำนวน occurrence ด้วย |
| P0 | `repair_original_font_cmaps()` บรรทัด 301 ตรวจ Identity-H แต่ใช้ GID เป็น key โดยไม่ตรวจ CIDToGIDMap อย่างชัดเจน | ต้องยืนยัน mapping ของฟอนต์ใหม่ที่ generator สร้าง หรือแปลง code→CID→GID ให้ครบก่อนเขียน ToUnicode |
| P0 | `repair_generated_thai_cmaps()` บรรทัด 24 ใช้ glyph index เป็น key เช่นกัน | ต้องมี contract และ regression test สำหรับ mapping นี้ ไม่ขยายใช้กับฟอนต์ทั่วไปโดยเดา |
| P1 | `lines()` บรรทัด 70 เก็บ bbox, origin, font, size, RGB และ flags | ยังไม่เก็บ source operators/text state ครบ จึงใช้เป็นโมเดลแก้แบบรักษาต้นฉบับทุกชนิดไม่ได้ |
| P1 | `change_lines()` บรรทัด 438 ลบและสร้างใหม่ทั้งบรรทัด | แก้ชื่อจุดเดียวอาจ reshape ข้อความอื่นในบรรทัด ต้องแยกช่วงแก้พร้อมบริบทที่จำเป็น |
| P1 | `insert_original_shaped()` บรรทัด 324 วางผลใหม่บนหน้า | ตรวจเพิ่ม clip, ลำดับการวาด, spacing และสีเดิม ไม่ใช่แค่ baseline กับ font hash |
| P1 | `merge_original_subsets()` ตรวจ outlines/metrics; comment ระบุ Merger ทิ้ง morx | ตรวจ shaping behavior หลังรวม ไม่ถือว่า Unicode mapping ทดแทน layout tables ได้ |
| P1 | `exact_local_font()` บรรทัด 225 ใช้ชื่อภายในและ cmap | ชื่อเหมือนกันยังอาจต่างรุ่น ต้องตรวจ metrics/รูปร่าง/รุ่น และแยกสถานะ “ไฟล์เดิม” จาก “ชื่อเดิม” |
| P1 | `reusable_font()` และ local-font path กรอง fsType ด้วย mask `2|256|512` | ยังไม่แยก preview/print-only (4) สำหรับการแก้; no-subsetting ถูกบล็อกทั้งหมด ควรทำ policy ตามชนิดสิทธิ์และการใช้งานจริง |
| P1 | `inspect()` บรรทัด 86 รวม signature flags/field เป็นสถานะเดียว | แยกมีฟิลด์แต่ยังไม่เซ็นจากมีลายเซ็นจริง ก่อนขยายการรองรับ |
| P1 | `apply()` full rewrite และ reopen ด้วย engine เดิม | เพิ่มการตรวจต่าง engine, semantic structures และกรณี resource ร่วม |

จุดที่ควรรักษาไว้จากโค้ดปัจจุบัน: มีการลบเนื้อหาข้อความจริงโดยไม่เติมสี่เหลี่ยมขาว, ไม่แก้เอกสารต้นทางเมื่อ operation ล้มเหลว, มีการตรวจการใช้ฟอนต์หลังจัดรูป, มี guard สำหรับบรรทัดซ้อนและหน้าหมุน สิ่งเหล่านี้เป็นฐานที่ดี แต่ยังไม่พิสูจน์ความถูกต้องของ PDF ทุกประเภท

## 11. สถาปัตยกรรมที่เสนอให้พัฒนาต่อ

```text
เปิดไฟล์และตรวจสิทธิ์/รุ่น/ความสามารถ
    → ดัชนี source runs + Unicode + geometry + resources
    → เลือก occurrence / รับข้อความใหม่
    → แผนแก้ไข: font resolution + shaping + พื้นที่ + ผลกระทบ
    → เขียน revision ชั่วคราวและ render PDF จริง
    → ตรวจข้อความ ภาพ และโครงสร้างที่เกี่ยวข้อง
    → commit revision เดียว / Undo / ส่งออก
```

เริ่มด้วย subset ที่พิสูจน์ได้: ข้อความแนวนอนสีทึบ ฟอนต์ที่มี mapping ชัด และไม่มี clip/structure ที่ยังจัดการไม่ได้ แล้วเพิ่ม capability ทีละชุด นี่เป็นข้อเสนอเพื่อควบคุมความเสี่ยง ไม่ใช่ข้อจำกัดถาวรของ PDF

UI ควรแจ้งสถานะก่อนผู้ใช้พิมพ์ว่า “ใช้ฟอนต์เดิมได้”, “ต้องเลือกฟอนต์”, “ข้อความนี้เป็นภาพ” หรือ “ต้องใช้โหมดเฉพาะ” แทนการปล่อยให้พิมพ์จนกดบันทึกแล้วขึ้นข้อความผิดพลาดกว้าง ๆ การลด error ที่รบกวนควรมาจากการตรวจล่วงหน้าและทางเลือกที่ชัด ไม่ใช่ซ่อนความผิดพลาด

ยังไม่จำเป็นต้องเปลี่ยน React/FastAPI/PDF.js ทั้งชุด ควรปรับ editing model และ validation ก่อน ส่วนการเลือกเพิ่ม PDF SDK หรือ parser ต้องประเมินความสามารถ ต้นทุน และใบอนุญาตแยกจากรายงานนี้

## 12. เกณฑ์ทดสอบก่อนเรียกว่าแก้ได้ถูกต้อง

| ชุดทดสอบที่เสนอ | ผลที่ต้องได้ |
|---|---|
| THSarabunPSK เต็ม/ฝัง subset/ไม่ฝัง | แสดง font provenance และใช้ glyph ถูกต้อง; ไม่มี silent fallback |
| ชื่อไทยมีสระ/วรรณยุกต์ และข้อความไทยอังกฤษ | ภาพถูก อ่านกลับถูก ไม่ตัด cluster ผิด |
| Identity-H กับ CIDToGIDMap ที่ไม่ identity | ToUnicode อ้าง character code ถูกต้อง |
| ชื่อฟอนต์เหมือนกันแต่ต่างรุ่น | ไม่อ้างว่าเหมือนต้นฉบับจากชื่ออย่างเดียว |
| ช่องว่างติดกัน NBSP compatibility characters | แยกนโยบายค้นหาและความถูกต้องหลังบันทึกได้ |
| ชื่อเดียวกันสองจุดในหน้าเดียว/หลายหน้า | จุดเดียวเปลี่ยนจุดเดียว; ทั้งหมดเปลี่ยนครบ; Undo ย้อนครบ |
| ชื่อแตกหลาย spans/operators | ค้นหาและเลือกขอบเขตได้ หรือแจ้งขอบเขตที่ยังไม่รองรับ |
| Tc/Tw/Tz/TJ และ baseline shift | ไม่เลื่อนส่วนที่ไม่ต้องแก้โดยไม่แจ้ง |
| Form XObject ใช้ร่วมหลายครั้ง | แก้หนึ่ง instance ไม่กระทบ instance อื่น |
| CropBox ไม่เริ่มศูนย์ Rotate และ UserUnit | พิกัดเลือกและผลลัพธ์ตรงกัน |
| Clipping, transparency, CMYK และข้อความเป็นเส้นขอบ | รักษาที่รองรับได้ หรือปฏิเสธก่อน commit |
| ActualText/tagged content และแบบฟอร์ม | ภาพกับข้อความเชิงความหมาย/ค่า field สอดคล้องกัน |
| ภาพสแกนมี hidden OCR | ไม่รายงานว่าเปลี่ยนภาพสำเร็จเมื่อแก้เฉพาะ hidden text |
| signature field ว่าง/ลงนามแล้ว/จำกัดสิทธิ์ | สถานะแยกถูกต้อง ไม่หลีกเลี่ยงข้อจำกัด |
| แทนที่ทั้งหมดแล้วบางจุดพื้นที่ไม่พอ | ล้มเหลวแบบ atomic พร้อมระบุจุด ไม่มีแก้บางส่วนเงียบ ๆ |

การตรวจต้องมีหลายชั้น: เปิดไฟล์ใหม่ ตรวจข้อความและจำนวน occurrence, ตรวจภาพก่อน/หลังเฉพาะพื้นที่ที่ควรเปลี่ยนและพื้นที่คุ้มครอง, ตรวจ resources/โครงสร้างที่เกี่ยวข้อง และเปิดด้วย renderer มากกว่าหนึ่งตัว เช่น MuPDF กับ PDF.js กำหนด tolerance ของภาพโดยคำนึงถึง antialiasing ไม่ใช้ pixel equality ข้าม renderer อย่างไม่มีเงื่อนไข

`qpdf --check` ช่วยตรวจโครงสร้างและ syntax แต่เอกสารของ qpdf ระบุว่าไฟล์ที่ผ่านยังมีปัญหาใน content หรือความสอดคล้องกับข้อกำหนดได้ จึงใช้เป็นหนึ่งด่าน ไม่ใช่คำรับรองทุกด้าน ดู [qpdf PDF Inspection](https://qpdf.readthedocs.io/en/stable/cli.html#option-check).

veraPDF ตรวจตาม profiles ของ PDF/A, PDF/UA และ WTPDF; การตรวจ PDF/UA ครอบคลุมส่วนที่เครื่องตรวจได้ ไม่ควรนำผลไปกล่าวว่าเป็นการรับรอง editor ตาม ISO 32000 ทั้งหมด ดู [veraPDF Validation](https://docs.verapdf.org/validation/).

## 13. ลำดับดำเนินการและสิ่งที่ยังไม่ได้ทำ

ข้อเสนอการพัฒนารอบถัดไป:

1. แก้ P0: verification ที่รักษาข้อความจริง ตรวจตำแหน่ง และยืนยัน code/CID/GID mapping
2. ทำ font capability และสิทธิ์ให้ชัดก่อนแก้ พร้อมเลือกฟอนต์ที่ค้นหาได้
3. เพิ่ม source-aware editing model และช่วง shaping เพื่อไม่สร้างใหม่ทั้งบรรทัดโดยไม่จำเป็น
4. ทดสอบ “จุดเดียว / ถัดไป / ทั้งหมด” กับ source runs และ resource ร่วม
5. ขยายไปยังพิกัดซับซ้อน Tagged PDF แบบฟอร์ม และเอกสารอื่นตามชุดทดสอบ

รายงานนี้ **ยังไม่ได้แก้โค้ด ยังไม่ได้รันชุดทดสอบใหม่ และยังไม่ได้รับรองว่าเทียบเท่า Acrobat Pro** ประเด็นในตาราง audit ต้องนำไปสร้าง regression tests และแก้ในงานพัฒนาต่อไป การศึกษา ISO ทำให้ระบุปัญหาและเกณฑ์ยอมรับได้แม่นขึ้น แต่ไม่ได้ทดแทน implementation และการทดลองกับไฟล์จริง

ช่องทางอ่านมาตรฐานต่อ: [PDF specification archive](https://pdfa.org/resource/pdf-specification-archive/), [Sponsored standards](https://pdfa.org/sponsored-standards/), [Normative references ของ ISO 32000](https://pdfa.org/iso-32000-normative-references/). เอกสารที่เปิดให้อ่านฟรียังมีเงื่อนไขลิขสิทธิ์ ไม่ได้หมายความว่าเป็น public domain รายงานนี้จึงเชื่อมไปยังต้นทางแทนการแจกสำเนามาตรฐาน
