# โหมดพิมพ์ตรงตำแหน่งข้อความ — ระยะที่ 1

เริ่มปรับการแก้ไขให้ใกล้เคียงโปรแกรมแก้ PDF บนเดสก์ท็อป:

- ดับเบิลคลิกบรรทัด โหลดไฟล์ฟอนต์ต้นฉบับจากเซิร์ฟเวอร์เข้า FontFace ของเบราว์เซอร์ พร้อมกำหนด ascent/descent
- ช่องพิมพ์โปร่งใสวางตาม baseline และขนาดต้นฉบับ ไม่เลือกทั้งบรรทัดอัตโนมัติ ผู้ใช้คลิกภายในข้อความเพื่อวางเคอร์เซอร์หรือเลือกคำได้
- พื้นหลังขณะแก้เป็น PDF สำเนาชั่วคราวที่ลบเฉพาะข้อความบรรทัดนั้น ไม่ใช้กล่องขาวปิดภาพหรือพื้นสี ไม่แก้ current/history จนกด Enter/บันทึก
- Esc คืนหน้าปัจจุบัน; ปิดและคืนทรัพยากรฟอนต์เมื่อจบการแก้
- Ctrl+Z / Ctrl+Y / Ctrl+Shift+Z ย้อนประวัติ PDF เมื่อไม่ได้พิมพ์ในช่องข้อความ ระหว่างพิมพ์ให้เบราว์เซอร์จัดการ undo ของข้อความ
- ไม่มีฟอนต์ที่ใช้ได้ หรือเบราว์เซอร์ปฏิเสธฟอนต์ จะแจ้งข้อจำกัดแทนการเลือกฟอนต์อื่น

## ผลตรวจ

Backend 32 tests ผ่าน รวมตรวจว่าการเตรียมบริบทไม่เปลี่ยน PDF/current/revision/undo และยังคงเส้นในเอกสาร Frontend 18 tests ผ่าน รวมพิกัด baseline, ขนาด CSS, เลือกเคอร์เซอร์, ปุ่มลัด และ workflow เดิม Production build ผ่าน

ยังไม่ได้ตรวจภาพหน้าจอและการ shape ฟอนต์จริงในเบราว์เซอร์ของผู้ใช้ การทดสอบ Frontend ใช้ DOM จำลองและจำลอง FontFace/API จึงไม่ใช่หลักฐานว่า browser shaping ตรง PDF ทุกกรณี ให้ตรวจผล PDF ที่บันทึกแล้วบนหน้าเอกสาร

## ขอบเขตที่ยังไม่เสร็จ

ยังแก้ทีละบรรทัด ไม่รองรับ reflow ย่อหน้า ลากย้าย/ปรับกรอบ หรือ style หลายแบบภายในบรรทัด และยังไม่วาง caret ตามตำแหน่งดับเบิลคลิกครั้งแรก (เริ่มท้ายบรรทัด แล้วคลิกวางตำแหน่งได้) ไม่ใช่ความสามารถเทียบเท่า Acrobat Pro ทั้งหมด

ฟอนต์ Base14 ที่ไม่มีไฟล์ TTF/OTF ใช้ซ้ำอาจเปิดการพิมพ์โหมดนี้ไม่ได้ ตัวอักษรใหม่ที่ไม่มีใน subset อาจแสดงด้วย fallback ของเบราว์เซอร์ระหว่างเป็นร่าง แต่ backend ยังคงปฏิเสธการบันทึกหากไม่สามารถใช้ฟอนต์เดิมได้ ขนาดพื้นที่ร่างอาจกว้างกว่าพื้นที่ที่ backend อนุญาต; การตรวจชนเนื้อหาและพื้นที่ยังทำเมื่อบันทึก

## เปิดใช้งาน

ส่งออกงานและคัดลอกร่างที่ต้องเก็บก่อนหยุด Backend จากนั้น Ctrl+C และเรียกคำสั่งเดิมใหม่ แล้ว Ctrl+F5 ในเว็บและเปิด PDF อีกครั้ง โหมดนี้ต้องใช้ endpoint `/api/editing-context` ใหม่ จึงรีเฟรชเว็บอย่างเดียวไม่ได้
